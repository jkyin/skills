# GuruClub MR 描述

让未读过对话的 reviewer 理解最终改动为何存在、会改变什么，以及验证到哪里。

## 写作

- 阅读本轮目标 MR 或已选分支的最终 diff 和必要证据。用户只要求文案时交付 Markdown；不顺带 commit、push、发布评论或改 MR。
- 简单改动用一两句说明问题与结果，再列实际验证；复杂问题按需增加根因、影响面、关键取舍和真实未处理项，不强制每个 MR 套全部标题。
- 可用具体触发场景解释前后行为；保留理解当前实现必需的反直觉选择。范围变化后重写标题和正文，删去无关对话过程与弃用方案。
- 描述最终实现，不逐文件复述 diff；不引用外部项目作对标，依赖名称及当前实现所依赖的技术契约可出现。
- 已完成检查与待 CI、真机或运行时验收分开；不要求为了撰写描述运行整套测试或格式化。只写有证据的结果。
- 真实未处理项写明影响与未纳入原因，没有则省略。冒烟建议给出具体操作，重点场景可加粗。

用户或项目提供有效模板时遵循其要求，详情可参考 [复杂 MR 写作](references/writing.md)。

## 标题与写入

`release/X.Y.Z` → `develop` 的标题固定 `release: X.Y.Z`。其他标题围绕最终问题与变化。

正文保存为 UTF-8 Markdown，保留真实换行。需要写入 GitLab 时读取 [写入与故障处理](references/gitlab-write.md)：确认本轮目标与授权，以 JSON 文件/结构化参数传正文，再回读标题与完整描述。

已明确要求更新指定 MR 的标题/描述时，准备完整文案后直接完成已授权写入，不因 skill 再次确认；仅索要描述草稿则不更新远端。缺少唯一目标时先完成本地文案再询问。

只撰写时以完整文案交付；写入时回报目标链接与核验结果。遇到认证或权限缺口保留文案和具体错误，不声称已写入。
