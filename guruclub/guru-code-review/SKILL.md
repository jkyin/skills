# Guru Code Review

审查本轮改动引入的问题，以证据过滤误报，以实际影响排序。默认置信度阈值 80，可用 `--threshold N` 指定 0–100。

## 确定审查对象

- 给定 MR URL 时，使用其 host、项目和 IID，按 [GitLab 取证](references/gitlab.md) 锁定当前 head、diff 和讨论/CI。未给目标时可查当前分支 MR，只有确实有多个合理目标才询问。
- 明确请求远程 MR 审查但认证、网络或权限失败，报告准确缺口；可继续已授权的本地辅助分析，不能将其冒充完整远程审查，也不切换 GitLab 浏览器自动化。
- 用户要求本地分支、工作区、暂存区或 commit 审查时，按 [本地范围与 base](references/local.md) 确定比较对象；不强求存在 MR 或安装 GitLab 工具。
- Draft、已合并、revert、lockfile 或相同 SHA 不自动成为跳过理由。明确要求复审就按本轮范围检查；可复用同一 head 的已核验证据，但重新读取会影响结论的讨论、CI、base 或用户补充。

## 建立上下文

从 diff 扩展到相关函数、调用方、状态/生命周期、依赖版本及测试，足以证明或推翻问题再下结论。需要时读完整文件，不强制每次全文件、全仓文档或固定数量的同类实现。

遵循当前客户端实际生效的项目指令。按改动需要读取贡献/审查规范及配置；另一客户端的文档可提供项目事实，但其专属运行指令不自动生效。规则冲突按适用指令优先级处理，无法裁决的项目约定不作为阻塞性发现。

依靠可复现路径或明确契约判断；风格偏好、diff 未引入的旧问题、已由 linter 覆盖的格式问题不凑数。已有抑制注释是设计线索，仍核实是否掩盖本轮真实回归。

检测到 Swift/iOS 相关改动时按需读取 [Swift 证据检查](references/lang/swift.md)，其他语言不套用该清单。不要为了证明完成而运行与风险无关的测试；受影响检查通过后收尾。

## 按风险选择复核视角

微小且确定的改动可由主 agent 直接完成。涉及跨模块契约、并发、依赖变化或较多独立路径时，在环境允许且有独立价值时委派复核，选择正确性、有效项目约定、历史回归或消费者契约等视角，不固定五个 agent 或重复规范检查。

委派遵守当前环境的协调规则与工具：Orca 规则适用时用真实 Run/Task/Dispatch，主协调负责消息、归属与收尾；其他环境使用获授权的调度能力。没有独立 agent 时可以顺序检查，但如实称为单 agent 复核。

每个复核任务提供目标 SHA、必要文件、范围和验收要求，返回路径、行号、触发条件、影响和证据；独立检查者不预先接收其他人的结论。主 agent 复核关键证据，去重并处理冲突。

## 发现与报告

- 置信度评价真实性，严重度评价影响；多个 agent 同意不能替代证据。仅猜测的路径不达到阈值，规则类发现必须引用有效规则及来源。
- 保留可证明的触发路径、文件/行号、后果和建议修复；信息缺失作为验证边界说明，不能写成已确认缺陷。
- 通过阈值后按实际影响分为 CRITICAL、IMPORTANT、SUGGESTION。不要把某个 API/代码模式一律定为 CRITICAL，也不为填满章节发建议。
- 默认简短报告：目标与 head/base、按影响排列的发现、实际检查及未验证范围。每条有稳定 ID 便于后续选择；详细候选评分和过滤记录可留本轮产物。
- 无达到阈值的发现时直接说明，并交代覆盖与缺口。报告中的 APPROVE 是审查意见，不等于执行平台批准动作。

## 评论与完成

默认只交付报告。`--comment` 表示希望进入评论流程，先展示具体发现；尚未选定要发送的内容时询问选择。若用户已明确要求发送本轮已展示的 ID/全文及目标，直接执行，不重复询问。

有具体评论授权时读取 [GitLab 评论](references/gitlab-comments.md)。默认创建 draft notes；公开发布/提交 review 仅按明确要求执行。评论、平台 approve 和 merge 的授权相互独立。

完成所请求的报告或评论写入后，回报目标、实际结果和验证边界。远程取证缺口、未完成的 worker 或未核实的写入均应如实列出，不用“已启动”代替完成。
