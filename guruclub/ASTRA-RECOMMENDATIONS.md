# GuruClub skills 改进建议

日期：2026-09-13。范围：本次导入的五类技能及两份 Code Review 差异文件。本文件保留首次建议及当时观察；建议已按用户授权实施，当前状态与验证见 [README](README.md)。下文“当前”均指首次检查时的源文件。

## 文章要点

OpenAI 的文章建议缩短且明确 skill 的触发描述，按任务需要加载支持文档，重新检查过度固定的执行步骤与审批边界，并写清任务完成条件。它也提醒：同一仓库可能服务不同模型，不能只按某个模型的能力删除必要指导。[官方原文：Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

下面是结合本地源文件作出的具体判断；优先保留已有业务约定，先修触发和执行边界，再做文字精简。

## 优先级 1：解决会改变行为的问题

### commit-expert：收窄触发与写入范围

当前 [SKILL.md](guru-commit/SKILL.md) 将“提到 git 相关操作”也作为触发条件，会把查看状态、解释命令等任务带入提交流程。建议 description 改为：

> 为 GuruClub 及其 iOS 库准备或执行已授权的 Git 提交，检查依赖引用并生成中文提交信息。

正文区分“只生成 message”“准备提交”“执行提交”“推送”。已经授权的同一提交范围不必机械重复确认；只要求 message 不执行 commit；commit 不隐含 push。

[formatting.md](guru-commit/references/formatting.md) 示例在全仓格式化后使用 `git add .` 并另建提交，可能把原本无关的工作纳入。建议只处理确认范围内的 Swift 文件，先展示格式化 diff；保留“格式化单独提交”的约定，但额外提交也应在授权范围内。文档或脚本变更不自动套用 SwiftFormat。

`AskUserQuestion` 是当前 Codex 工具列表没有的名称；应按环境选择可用交互方式。`argument-hint` 的跨客户端兼容性也应单独处理，不能假设 Claude 字段被所有 Codex 校验器接受。

### 周报与月报：统一空回答语义，保留明确调用

[周报](guruclub-weekly-report/SKILL.md) 写明未确认不收集；[月报](guruclub-monthly-summary/SKILL.md) 同时写了“先确认”和“工具空答案就按默认继续”。这两个工作流在用户没有回答时会产生不同结果。

建议把“用户确认范围”与“可自行采用默认值”区分清楚。如果保留范围确认作为必要门槛，就使用能保持问题待答的交互方式，取消、超时或空回答不算确认；用户已在同一流程确认的范围回答继续生效。是否允许参数齐全时跳过首次弹框，是用户偏好变更，不能仅凭文章建议直接删除现有要求。

保留周报、月报的 `allow_implicit_invocation: false`、来源可替换、本人工作归属、iOS 实质成果口径及 Confluence 目标区域限制。Confluence 的内容预览、写入草稿和正式发布应各自有明确边界，已有授权不要因保存或逐行验证再问一次。

### guru-code-review：先统一来源，再校正 base 与平台边界

当前两套 references 已经分叉。先合并经过验证的规则，再让安装入口统一指向维护源，避免同一请求在两个客户端得到不同结果。

本地 base 不应只凭同名 upstream、分支名字或“最近距离”直接定论：upstream 可能只是当前 feature 的远端副本。建议优先采用用户给出的比较目标；MR 模式使用 MR 的目标分支信息；本地模式展示候选与依据，确实无法确定才询问。明确请求远程 MR 审查但认证失败时，应报告证据缺口，不能把本地 diff 结果当成已完成远程审查。

## 优先级 2：减少固定流程与上下文负担

| 技能 | 当前观察 | 建议 |
| --- | --- | --- |
| Code Review | 243 行入口；列举大量触发同义句；固定 A1–A5，其中两个规范视角重复 | description 压成任务与边界。按改动风险选择独立视角，保留关键路径复核，调度工具服从当前运行环境和适用的协调规则。不能把同一 agent 顺序重读说成独立审查。 |
| Code Review | 每个改动文件完整读、找同类实现、加载两套规范 | 从 hunk 扩展到相关函数、调用方、生命周期和有效项目规则；缺上下文再扩大。保留防误报证据要求，不按文件数机械决定覆盖。CLAUDE 文档可以作为参考证据，其客户端专属指令不自动成为 Codex 行为约束。 |
| Code Review | 固定长报告、“做得好的地方”、待办和丢弃数量 | 主报告优先展示可行动发现、路径、证据、验证边界；空结果可简短说明。候选评分和去重细节可留内部产物，报告长度与实际发现匹配。 |
| 周报 | 90 行入口混合汇总、提醒、Confluence 和某个周五提醒配置 | 入口保留触发、范围、写作口径和完成条件；提醒/外部写入细则按需引用。具体运行时间由 automation 配置维护。 |
| 月报 | 129 行入口已有统计脚本和 references，但统计细节仍较长 | 保留三分之一门槛和状态口径摘要；第一父链、活跃日计算细节放到取证 reference，由脚本确定性执行。不要修改业务阈值。 |
| MR 描述 | 92 行入口把小改动也套入长模板，要求记录部分迭代经过和弃用方案 | 简单 MR 用问题、结果、验证；复杂问题按需展开根因和取舍。发布前以最终 diff 重写，只保留理解当前实现必需的历史。 |

上述按需加载和避免固定长流程的方向来自官方文章；具体拆分位置与优先级是本次检查的建议，并非官方要求的行数或固定模板。[官方原文](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 优先级 3：保留经验，移走易过期假设

- MR 描述里的“op 包装 glab 挂起”“keychain 凭据恒 401”属于特定环境经验。改为遇到对应现象才读取的故障说明，并报告当次实际错误，避免未验证就把工作交还用户。
- MR 描述末尾引用 `/code-formatter`，本次技能目录清点未发现同名 skill。应改为项目格式化配置或可用引用，并避免强依赖缺失技能。
- 自建 GitLab 的 host、分页、diff 定位与 JSON 文件输入，以及 Confluence 的表格结构保护、全文回读和保存证据，均有具体作用，应保留。
- 月报“三分之一活跃日”“tag 对应已上线”等是既定统计口径，应保留并明确其证据边界。代码被 tag 包含不代表已核实 App Store 发布。
- 用户提供的 Orca 协调规则已经限制适用环境，并区分微小工作与批量执行。建议保留角色、授权、文件所有权、worker 完成证据及 coordinator 收尾职责；容易变化的 CLI 细节交给运行时匹配的指南，不复制到每个业务 skill。

## 验收建议

下一轮修改用少量真实场景回放：只生成 commit message、不重复询问已授权的提交、未确认范围时不采集报告资料、只保存指定 Confluence 草稿、远程 MR 认证失败、feature upstream 导致 base 歧义，以及小 diff 与复杂并发 diff 的审查资源分配。比较错误动作、误报、遗漏和多余停顿，不用“字数减少”代替行为改善。

建议实施顺序：统一源码入口 → 修触发与授权边界 → 精简 Code Review → 精简周报/月报/MR 描述 → 场景回放验证。
