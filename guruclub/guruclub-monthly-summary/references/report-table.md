# 月报三列表格


正文列名固定为 **目标 / 结果 / 自评**，完整列出确认纳入的任务，不预设行数。

| 列 | 写法 |
|---|---|
| 目标 | 一句话需求或任务标题，直接说明要解决什么问题。 |
| 结果 | 先写状态，再写通过什么方式完成了什么、带来什么变化。偏业务和使用体验，尽量不用文件名、类名、提交号或实现细节。 |
| 自评 | 写过程与判断：难度、结构设计、如何发现旧问题、根因与修复方式、风险控制或验证边界。可适度技术化，但不要罗列代码名。 |

不要空泛写“高质量完成”“显著提升”；没有测量就不编造性能、耗时、崩溃率等数字。编译通过、CI 通过、真机通过、上线互不替代。描述修复过程的证据不足时采用保守措辞。

格式示例，**不代表应纳入的任务**：

| 目标 | 结果 | 自评 |
|---|---|---|
| 修复播放结束后封面显示异常 | **已交付**<br>播放结束时移除残留画面并恢复业务封面，避免封面信息被遮挡。 | 沿状态变化定位到结束事件未触发清理的问题，统一结束处理，并检查异步回调与资源释放的先后顺序。 |

正文前简要注明统计截止日、范围和活跃日口径。正文后另附低占比项目表；没有候选项就明确说明无需评估。边界或例外只解释必要信息，不附 GitLab 状态和链接。

单一来源保存为本轮 `outputs/<source-key>-YYYY-MM-monthly-summary.md`，多来源使用 `outputs/monthly-summary-YYYY-MM.md`。仅默认来源时仍使用 `guruclub-YYYY-MM-monthly-summary.md`。多项目仍保持三列，必要时在目标中简短标注项目以消除歧义。同月重复执行时保留有价值的既有确认和备份，不丢失用户修改。优先交付 Markdown，不另造未要求的表格文件或演示文稿。
