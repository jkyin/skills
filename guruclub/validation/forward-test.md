## 场景 2：do，仅提交已看过的 Swift 修复

模拟答复：将只提交已确认的修复 hunk，复用本轮已通过的范围内 lint，保留同文件无关修改；提交后报告 SHA 和未推送状态。

拟执行动作：

1. `git status --short`、`git diff --cached`、`git diff -- <修复文件>`，核对已确认 patch/message 与当前状态未变化；读取本项目适用的格式配置。lint 证据与 patch 对应时不重复扩大测试。
2. 对精确修复 patch 做 `git apply --cached --check <patch>`，再 `git apply --cached <patch>`，通过 `git diff --cached` 和 `git diff --cached --check` 确认暂存仅含授权修复。不能直接整文件 `git add`，不能格式化混有无关行的整文件。
3. 若原索引为空或只含本修复，按已批准 message commit。若存在其他已暂存内容，采用可隔离索引的提交方式并核验原索引内容得到保留，或明确报告具体无法隔离的冲突；不取消用户暂存，也不把它一起提交。
4. 回读新 SHA、提交 patch 和剩余工作区，确认同文件无关行仍未提交。不 push。

停止/完成条件：修复 patch 精确一致才提交；若 patch 漂移或索引冲突影响范围，暂停相关提交并提出具体冲突。成功时给 message、真实 SHA、lint 边界和“未推送”。不再以缺少第二次确认阻塞。

结论：通过。格式化未产生必要修复时不创建 style 提交；已通过 lint 不触发新增授权问题。
