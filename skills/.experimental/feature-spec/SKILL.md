# feature-spec

把模糊需求变成规格，再把规格变成可验证的实现。跨 agent 通用（Claude Code / Codex / 其他支持 `SKILL.md` 的 agent）。

Claude Code 通过 `disable-model-invocation: true` 禁止模型自动调用；Codex 通过 `agents/openai.yaml` 中的 `allow_implicit_invocation: false` 实现同样的限制。其他 agent 可能忽略这些平台字段，只能依赖 description，不能保证完全禁止自动触发。

## 核心原则

1. **上下文是稀缺资源。** 让主线程保留目标、决策和进度；把大范围、可独立的调查放到隔离上下文。
2. **可验证性决定自主性。** 完成条件必须可观察、可复核；项目支持自动化时优先使用命令和测试，不支持时写清人工步骤与预期结果。
3. **关键决策要落盘。** 用 `SPEC.md` 保存范围、假设、非目标和验收标准，使它成为跨 session、跨 agent 可传递的依据。
4. **规格改变要显式。** 实施中发现事实与规格冲突时，区分可安全适配的实现细节和会改变需求语义的决策；后者必须先确认。

---

## 阶段 0：分诊

显式调用本 skill 不等于必须走完所有阶段。先判断任务是否值得写规格。

**仅当以下条件全部满足时，跳过完整流程并直接实施：**

- 目标、预期行为和改动范围可以用一句话准确描述。
- 没有未决的产品、数据、兼容、安全、隐私或不可逆决策。
- 失败路径明确，且能立即写出可复核的验证方法。

跳过时，先用一句话说明原因，不创建 `SPEC.md`，然后直接完成并验证改动。

**满足任一条件就走完整流程：**

- 目标、范围、交互或失败行为仍有歧义。
- 涉及跨模块状态流转、公共接口、数据迁移、并发、权限、安全、隐私或不可逆操作。
- 需求出现「顺便」「兼容一下」「类似 XX 那样」「先简单做一下」等范围扩张信号。
- 不能说明如何验证完成，或不同验收方式会导向不同实现。
- 需要修改不熟悉的模块，且没有可信的相似实现可参考。

文件数量和“以前做过类似事情”都不能单独作为跳过规格的依据。不确定时走完整流程。

---

## 阶段 1：探索（只读 / 计划）

进入只读或计划阶段，读取代码和文档，不修改产品文件：

| Agent | 进入方式与边界 |
|---|---|
| Claude Code | 使用 `/plan` 或 `Shift+Tab`；Plan mode 阻止源码编辑，但仍以当前权限与版本行为为准 |
| Codex | 使用 `/plan` 或 `Shift+Tab`，让 Codex 收集上下文、澄清问题并形成计划 |
| 其他 | 使用等价的只读 / 计划模式；没有硬性模式时，在提示词中声明只读并将其视为软约束 |

**按需使用 subagent。** 当探索需要读取大量文件、涉及陌生模块，或调查可以独立切分时，用 subagent 隔离噪声；范围小且路径明确时由主 agent 直接探索，避免不必要的成本。

探索目标：

```text
探索仓库，找出与 <需求> 相关的：
- 现有模块、数据模型与状态流转
- 最接近的相似实现及可复用约定
- 失败路径、边界条件与兼容面
- 可执行的构建、测试、lint 或手动验证入口

只回报实际读取到的文件路径、关键行号和结论。
把“已确认”与“推测 / 待确认”分开；不要用通用工程建议替代仓库证据。
```

使用 subagent 时，把上述目标作为独立任务，只让它回传摘要与证据，不让它修改文件。

---

## 阶段 2：访谈

基于探索结果，询问只有用户能决定、且答案会实质改变范围或实现的问题。不要询问能从仓库、文档、设计稿或工具中直接查到的事实。

```text
我要做 <一句话需求>。基于探索结果访谈我。

只询问会改变范围、UI/UX、数据模型、兼容策略、失败行为、迁移方式或验收标准的问题。
挑战我的假设，指出互相冲突的要求和尚未覆盖的边界。
一次问一小组；每轮总结已确认决策和仍未解决的问题。
```

- Claude Code：需要结构化选项时要求使用 `AskUserQuestion`。
- Codex：在 Plan mode 中收集澄清信息；使用当前客户端提供的用户输入机制。

这一阶段的产出是**决策、假设和未决问题**，不是实施步骤。没有会改变结果的未决问题时结束访谈，避免为了“覆盖完整”无限追问。

---

## 阶段 3：写 SPEC.md

先检查仓库是否已有规格目录或模板。遵循现有约定；没有约定时使用任务工作目录中的 `SPEC.md`。如果目标文件已存在，不要覆盖，改用明确的功能名或先征求用户意见。

规格必须自包含：点名涉及的文件和接口，写明非目标、假设、风险与验证方式。

模板以 Goal、Context、Constraints、Done when 四要素为骨架：

```markdown
# <需求名>

## Goal
<要改变或建成什么。写成结果而不是方法。>
<成功时用户或系统能观察到什么。>

## Context
- `path/to/A.ext` — 现有的 XXX 逻辑，本需求需要复用/扩展
- `path/to/B.ext` — 照这个文件的分层与命名风格实现
- <相关文档 / 报错 / 设计稿 / issue 链接>

## Constraints
- 遵循仓库现有架构与适用的 AGENTS.md / CLAUDE.md
- 分支或工作树约束：<如适用>
- 依赖、平台版本、线程模型、权限或兼容要求：<如适用>

## Non-goals
- 不做 <X>
- 不改动 <Y 模块>；如确需修改，先确认范围变化

## Assumptions and open questions
- 已确认假设：<有证据支持的前提>
- 未决问题：<实施前必须解决；没有则写“无”>

## Requirements
1. 当 <条件> 时，系统应产生 <可观察行为>
2. 当 <失败 / 边界条件> 时，系统应 <可观察行为>

## Risk controls（按需保留）
- 兼容与迁移：<旧接口、数据、灰度、回滚>
- 安全与隐私：<权限、敏感数据、外部发送>
- 可观测性：<日志、指标、错误呈现>

## Done when
- [ ] `<可执行检查命令>` 通过（项目支持时至少一项）
- [ ] <关键路径及边界条件> 有自动化测试或说明无法自动化的原因
- [ ] <端到端手动步骤> 得到 <明确预期结果 / 截图 / 日志>
```

Done when 必须**可观察、可复核**，不能写成「代码质量良好」「体验正常」等形容词。项目能自动验证时至少包含一个命令；UI、硬件、外部系统等无法完全自动化的场景，写清操作步骤、预期结果和证据。

### 规格确认门

写完后先自查并向用户汇报：

1. 一句话目标与非目标。
2. 关键假设和风险。
3. 尚未解决、会改变实现的问题。
4. Done when 是否真的能执行或复核。

除非用户已明确授权全自动实施，且没有会改变需求语义的未决问题，否则得到用户确认后再进入实施。用户要求修改规格时，先更新 `SPEC.md`，再继续。

## 阶段 4：实施

### 选择 session

Claude Code 与 Codex 的官方建议并不完全相同，按平台和上下文健康度选择：

| 情况 | 做法 |
|---|---|
| Claude Code，规格已自包含且已确认 | 官方建议开新 session，用 `@SPEC.md` 引入，保持实施上下文干净 |
| Codex，仍是同一个连贯目标 | 优先留在同一 task，保留探索与决策轨迹 |
| 任务真正分叉、需要独立并行，或当前上下文已被无关内容 / 失败尝试污染 | fork 或新 task；并行写代码时使用独立 worktree |
| 其他 agent | 根据是否能可靠恢复规格、权限和仓库状态选择；不要假设所有平台都支持同样的 session 语义 |

一个 task 对应一个**连贯结果**，不是整个项目。只有工作真正分叉或上下文已不再帮助当前结果时才切换。

### 实施提示词

```text
按已确认的 @SPEC.md 实施。

分阶段推进，每阶段结束时：
1. 运行该阶段相关的 Done when 检查
2. 记录实际命令、退出状态和关键输出；手动验证记录步骤与结果
3. 检查失败时先定位根因，再在不改变需求语义的范围内迭代

如果现有实现与 SPEC.md 冲突：
- 只是实现细节，且可在不改变范围、接口、数据、兼容和验收标准的前提下安全适配：继续，并记录采用的方案
- 会改变上述任一项：停下来说明冲突、证据和选项，等待确认

同一阻塞重复出现或安全路径已穷尽时，报告根因和已尝试证据。
不得删除测试、降低断言、篡改验收标准或无限重试来制造“通过”。
```

### 把关卡硬化（可选）

1. **提示词内验收**：要求运行检查、展示证据并在安全范围内迭代。日常需求默认使用这一层。
2. **Goal mode**：
   - Claude Code 的 `/goal <condition>` 使用独立评估器逐轮检查；条件必须能从对话证据判断，并为长任务加入轮次或时间上限。
   - Codex 的 `/goal` 为当前 task 保留持续目标；继续在同一 task 中补充约束和状态，不假设其评估机制与 Claude Code 相同。
3. **Stop hook**：Claude Code 和 Codex 都支持。只把稳定、可重复的门禁固化为 hook；优先用确定性命令，不把一次性需求写成全局 hook。

这些机制不会扩大权限，也不能替代清晰的规格和真实验证。

### 计划中途要改

- Claude Code：Plan mode 中可用 `Ctrl+G` 在编辑器里直接修改计划。
- 通用：直接修改 `SPEC.md`，记录范围或验收变化，再让 agent 重读；不得只在对话中留下与磁盘规格冲突的新决定。

## 阶段 5：审查

重要改动优先使用独立上下文审查，使审查者按 diff、规格和仓库证据判断，而不是沿用实现者的解释。小而机械的改动不必为了“独立”强制创建新 session。

| Agent | 方式 |
|---|---|
| Claude Code | `/code-review` 用 fresh subagent 审当前 diff；`/review [PR]` 审本地 PR；也可显式要求 subagent 对照 `SPEC.md` |
| Codex | `/review` 可审基线分支、未提交改动、某个 commit 或使用自定义指令 |
| 其他 | 使用独立 reviewer/subagent；没有时另开 session，只提供 diff、`SPEC.md` 和必要仓库上下文 |

审查提示词：

```text
对照 @SPEC.md 审查这个 diff。检查：
- 每条 requirement 是否实现
- 边界与失败路径是否有测试或可复核证据
- 是否改动 SPEC.md 范围之外的行为
- 验证结果是否真实支持完成声明

只报告影响正确性、安全性、兼容性或既定需求的缺口。
风格偏好和 CI 已确定性检查的事项不要重复报告。
每条发现必须给出文件位置、触发条件和影响。
```

审查者被要求找缺口时通常会产出一些候选。只保留能被代码或运行证据支持、且影响既定要求的发现；其余标为可选建议，不为了消除所有评论而过度工程。

## 阶段 6：复盘与沉淀

### 当下修复

同一个问题连续纠正仍失败时，先判断根因：

- 规格或提示词缺少约束：更新 `SPEC.md` 或初始提示。
- 仓库事实判断错误：补充代码、日志或运行证据。
- 对话包含互相冲突的旧方案，或上下文已明显臃肿：compact、`/clear` 或开新 task，并用修正后的规格重新开始。
- 仍属于同一个连贯问题且历史有价值：保留当前 task，不要只为“干净”丢掉有用决策。

### 长期沉淀

重复错误不一定都应该写进 `AGENTS.md` / `CLAUDE.md`。先选择正确的承载面：

| 内容 | 承载位置 |
|---|---|
| 稳定的仓库约定、非显然命令、长期架构约束 | `AGENTS.md` / `CLAUDE.md` |
| 能机械判定的要求 | 测试、lint、类型检查或 hook |
| 跨任务重复出现的操作流程 | skill |
| 一次性需求、临时决策、当前实现范围 | `SPEC.md` / issue / task |
| 易变化的外部事实或完整 API 文档 | 官方链接或项目文档，不复制进记忆文件 |

只有观察到稳定、重复的模式后才提出长期规则。除非用户明确要求，不要自动修改持久化指令文件；先给出一条具体、可执行的候选规则和证据。

候选规则提示词：

```text
这个问题已重复出现。做一次复盘：
1. 根因是规格、仓库事实、缺少机械门禁，还是缺少持久规则？
2. 最小且正确的承载面是什么？
3. 如果应写入 AGENTS.md / CLAUDE.md，只给出一条具体、可执行的候选规则及证据，不直接写文件。
```

**持久化指令的纪律：**

- 保持简短。删掉不会导致重复犯错的内容。
- 只写 agent 无法从代码直接推导、且长期稳定的项目事实。
- 不写标准语言约定、一次性实现细节、经常变化的信息或「写整洁代码」等空话。
- 外部平台、API、政策和安全规则必须保留可追溯来源，并在可能变化时重新核对。

**文件位置：**

| Agent | 持久化指令 | Skill 目录 |
|---|---|---|
| Claude Code | `CLAUDE.md`（项目根、用户级或子目录） | `.claude/skills/` |
| Codex | `AGENTS.md`（仓库根、`~/.codex/` 或子目录，就近规则生效） | `.agents/skills/`（团队）、`$HOME/.agents/skills`（个人） |

跨 agent 共用规则时，使用一个明确的规范源和可验证的同步方式。不要假设不同 agent 都支持相同的 import 语法；只有在目标工具和环境确认支持时才使用软链接或 import。

## 常见失败模式

| 症状 | 根因 | 处方 |
|---|---|---|
| 小 diff 引入高风险行为 | 只按文件数量分诊 | 改用数据、兼容、安全、权限和不可逆风险判断 |
| 实现得很漂亮但解决错了问题 | 跳过探索、访谈或规格确认门 | 回到仓库证据和未决决策，不在错误方向上补丁 |
| 完成声明无法复核 | Done when 是形容词或只有口头保证 | 改成命令、测试结果或明确的手动步骤与预期 |
| 检查一直失败却仍声称完成 | 无限重试或降低验收标准 | 报告根因和证据，不删测试、不弱化断言 |
| 同一问题反复出现 | 没找到正确承载面 | 在规格、测试/hook、skill、持久规则之间正确分流 |
| 越到后面越偏离目标 | task 混入无关工作或大范围探索挤占上下文 | 一个 task 对应一个连贯结果；大范围独立调查按需用 subagent |
| 审查报告很多但缺少证据 | 没限定发现范围和证明责任 | 只保留影响正确性、安全性、兼容性或既定要求的可证实缺口 |
