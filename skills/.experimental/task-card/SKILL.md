# 任务卡

把「顺带发现、但超出本次改动范围」的问题，写成一张**离开当前对话也能执行**的卡。

## 何时开卡

**开：** 死代码、过期文档、缺失的测试覆盖、已确认 TODO、顺带发现的安全问题；当前改动能一并修但会让 diff 失焦的；MR 描述里「已知未处理项」的每一条（一条一张，别合并）。

**不开：**

- 模糊的代码异味、低置信度猜测（「这里*可能*有问题」）
- 现在顺手就能改完的琐碎项——直接改
- 需要产品决策而非工程动作的
- **已有卡 / issue / TODO 条目覆盖同一问题的**——去补充那张，别新开

**判据：能不能写出「可复核的证据」+「可执行的第一步」。** 写不出，说明还没查清楚——要么先查，要么别开。开一张自己都说不清的卡，只是把困惑转交给别人。

**开卡前先查重**：搜项目 TODO 文档与 issue，回看本会话是否已开过同题的卡。

## 骨架（六段）

```
1. 定位   项目绝对路径（多工作树写清哪个树）；从哪个分支切——默认主干，
          若问题只存在于当前分支，明写「必须从 <branch> 切，主干上没有这段代码」
2. 问题   一句话说清「什么坏了 / 什么该清理」
3. 证据   file:line、grep 完整命中、继承链——可被独立复核；分「已确认 / 未验证」两栏
4. 任务   编号步骤；含判定分支（见下）；末尾写「完成判定」——做到什么程度算做完
5. 约束   只写与这张卡相关的 1–3 条（从项目文档取，别从本文件抄）
6. 来源   MR / issue 链接；没有就写分支名 + commit sha + 当时在做什么
```

证据可以紧跟问题句写，但不能因为「问题已经说清楚」就省掉。**第 3、4 段一个都不能省**——省掉证据就成了传闻，省掉步骤就成了抱怨。

一批卡之间有先后时（先补测试再删死代码），在第 4 段写明前置；无依赖就写「可独立开工」。卡片列表本身不表达顺序。

## 三个决定成败的点

### 1. 任务段必须带判定分支

接手的 agent 没有你的上下文，会在**你没验证过的前提**下动手。凡结论依赖某个前置事实的，都写成分支：

> 「先核实**目标分支上该问题是否仍存在**（当前发现基于 commit `<sha>`）；
> 　**若已被其它改动修掉**：只回报结论，不要动代码；
> 　**若仍在**：按下列步骤执行。」

反例：「这块死代码删掉」——接手者不知道「可删」的前提是没有反射 / 字符串按名调用，会直接删到跑不起来。

### 2. 证据必须能被独立复核

贴 grep 的**完整命中列表**、行号、继承链，让接手者自己跑一遍就能验证，而不是要求他信你。同时**写清你查到哪儿为止**——虚报确定性比漏报更糟：

> 已确认：`grep -rn "legacyBadgeSync" Sources/` 全仓 3 处——
> 　`FooVC.swift:412`（定义）/ `:517`（唯一调用，在 `if false` 分支内）/ `:631`（注释）；
> 　`--include=*.m` 0 命中，无 selector 字符串引用。
> 未验证：是否存在运行时 KVC / 远端配置按名调用。

反例是「我发现这段好像没人调用」——接手者要么盲信，要么从头再查一遍，卡就白写了。

日志片段和 grep 命中里的 token、手机号、用户 ID **先脱敏**——卡可能被贴到 issue / MR 上。

### 3. 完成判定必须可观察

写「grep 该符号全仓 0 命中」「该文档与 X 接口签名一致」，不写「清理干净」「优化一下」。

## 落地

### 有任务派生工具时

**判据只看工具列表里有没有 `spawn_task`（全名 `mcp__ccd_session__spawn_task`），不看自己是哪个 agent**——同为 Claude Code，未挂 `ccd_session` MCP 的会话也没有它。

它是非侵入的：只挂出一张待用户点击的卡片，**当前回合继续，不用停下来问**。一张卡一次调用，别把多条塞进同一个 prompt。

| 字段 | 给谁看 | 约束 |
|---|---|---|
| `title` | 卡片标题 + 新会话标题 | < 60 字，**动词开头的祈使短语**（「清理…」「评估…」「补上…」） |
| `tldr` | 悬停提示，给**人** | 1–2 句白话说清「会做什么、为什么」；**不放路径和代码** |
| `prompt` | 新会话首条消息 | 上面的六段骨架。卡片上不渲染、可以长，但它是**新会话可见的首条消息**——别塞密钥 token |
| `cwd` | 新会话的工作目录 | **必填**。填卡片实际要动的那个仓库根（跨仓时不是当前仓）；**绝不要填临时 worktree 路径**——它会被删 |

`cwd` 要与骨架第 1 段的绝对路径一致；写不出这个路径，说明定位段还没查清楚，先别开卡。
`tldr` 常见错误是写成 `title` 的复述——它该回答的是「我为什么要点这个」。

**开完不是结束：** 记下返回的 `task_id`。同一会话里问题被顺手修掉、或被更准的卡取代 → 用 `dismiss_task` 撤回；**替换顺序是先开新卡、再撤旧卡**。用户已点开或已处理的撤不掉，失败就到此为止、**不要重试**。`task_id` 不跨 app 重启保留，长期待办要同时落进项目 TODO 文档，不能只靠卡片。

### 无任务派生工具时

工具列表里没有 `spawn_task` 时走这节（Codex、未挂该 MCP 的会话等）。骨架不变，只换出口。**能问就问用户要哪个出口；非交互运行（`codex exec`、CI、子 agent）无从问起时，默认只贴在回复里——不写文件、不发平台评论。**（前一节不用问，是因为挂一张卡片没有副作用；下面这些会留痕。）

- **贴在回复里**：整张卡放进一个围栏代码块，让用户能整块复制进新会话；多张卡各自一块
- **写成 markdown 文件**：默认落系统临时目录、**不落工作树**，用户明确指定仓库内路径才例外；无论落哪都**不要 `git add`**，并把**绝对路径**回报给用户
- **落到 issue / MR 评论**：走该平台 CLI，注意中文多行要走文件而非命令行参数
- **追加进项目既有的 TODO 文档**

## 约束段（第 5 段）怎么写

**去项目自己的 `AGENTS.md` / `CLAUDE.md` / 记忆 / 既有 skill 里取，不要从本文件复制。** 每个项目的硬约定不同，抄错了比不写更坏。

只写与这张卡相关的 **1–3 条**，优先写「新会话读了项目文档也未必知道」的东西——历史债、被推翻过的方案、本次的权限边界。项目文档里 agent 自己会读到的通用规范不用重抄。

常见类别：提交与格式化、验证边界（哪些跑哪些明确不跑）、权限边界（能否自行 commit / push / 开 MR）、该场景特有的坑。写成祈使句，别写成「建议」。

## 写完自检

1. 把这张卡单独拷进空白会话，接手者能不能不问你就复核证据？问得出来 = 证据不够。
2. 第一步是不是可执行动作？凡结论依赖前置事实的，有没有「若…则不要动」？
3. 完成判定可观察吗？`title` 动词开头且 < 60 字、`tldr` 里没有路径和代码、`cwd` 填了吗？

## 相关

- **`handoff`（若你的 skill 列表里有）**：把**整个会话**压缩成交接文档（换 agent 继续同一件事）。本 skill 是**单个越界发现**拆成独立任务；列表里没有它就忽略本条。
- **`guru-mr-description`**：分工是——写描述正文走它，把其中每条「已知未处理项」变成可独立执行的卡走本 skill，两边应一一对应。
- **`to-issues` / `triage`**：面向 issue tracker 的批量拆分与状态流转，需显式调用；本 skill 是单张、随手、不绑定 tracker。
- **`commit-expert`**：开卡不涉及暂存 / 提交。「这条残留不提交、开个卡」——开卡部分走本 skill，提交部分才走它。
- **`dws`**：那里的「创建待办」指钉钉待办，不是任务卡。
