# Refactoring UI

把 Refactoring UI 的界面设计方法变成可执行的流程。核心立场：好看主要来自**层次、间距、约束好的系统**，而不是天赋或装饰。

- 逐条原则与正反例：[references/principles.md](references/principles.md)
- 可直接落地的刻度与数值（间距、字号、色板、阴影、对比度）：[references/tokens.md](references/tokens.md)
- 审查清单（按影响排序）：[references/review-checklist.md](references/review-checklist.md)

先判断是哪种模式，再按对应流程走。需要具体数值时读 tokens.md，需要解释「为什么」或找替代做法时读 principles.md。

## 模式一：设计（从零或重做）

按这个顺序决策，前一步没定不要纠结后一步：

1. **先做功能，不做外壳。** 从一个具体功能（「搜索航班」需要哪些字段和按钮）开始，不先画导航栏、侧边栏、整体布局。外壳等做完几个功能后再定。
2. **做最小可用版本。** 不在设计里预埋还没准备好实现的功能；难实现的部分推迟。小步循环：设计 → 实现 → 用真实界面发现问题 → 回到设计。
3. **定个性。** 用字体（衬线=优雅/经典，圆润无衬线=活泼，中性无衬线=朴素）、主色、圆角（无圆角=正式，大圆角=活泼，全局保持一致）、文案语气表达。参考目标用户常用的产品，但别照搬直接竞品。
4. **先套系统再画。** 项目已有 design token 就用现有的；没有就从 tokens.md 取默认刻度（间距、字号、字重、文字色、灰阶、阴影），只在刻度内选值。
5. **先灰度、后上色。** 先只用间距、对比度、字号、字重把层次做出来；层次成立后再引入颜色强化。
6. **从过量留白开始往回收。** 每个元素先给明显偏多的空间，再逐步减少到合适；组间距必须大于组内间距。
7. **建立层次。** 每屏只有一个最重要的东西和一个主操作；用字重和颜色而不是只靠字号拉开主次；弱化竞争元素，而不是一味加强主元素。
8. **加深度与细节。** 用阴影表示 Z 轴高度（按钮小、下拉中、弹窗大）；需要「精致感」时再用强调边框、背景色变化、自定义复选框等手法，最后检查空状态。

在刻度里挑值时用「排除法」：先猜一个，再试两侧相邻值，选三者里明显最好的；若最好的是边上那个，就以它为中心再比一轮。

## 模式二：审查（给截图、页面或 UI 代码）

1. 先看全局：一眼能否说出这屏最重要的是什么、主操作是哪个。说不出就是层次问题，优先级最高。
2. 按 [references/review-checklist.md](references/review-checklist.md) 从上往下查：层次 → 间距与分组 → 文字 → 颜色与对比度 → 深度 → 图片 → 细节。前面的问题没解决，后面的修饰意义不大。
3. 每条发现写成「问题 → 依据的原则 → 具体改法（带刻度内的具体值）」。改法要可执行，例如「日期从 14px 浅灰改成 16px、颜色换成次要文字色（白底上仍满足 4.5:1），标题保持 18px 但字重 600」，而不是「加强层次」。
4. 读代码时直接对照数值：任意 px 值、刻度外的字号、`lighten()/darken()` 临时色、白色半透明文字、彩色底上的灰字、到处是 1px border、`align-items: center` 对齐不同字号文字、居中的长段落，都是高频问题。
5. 输出按影响排序，最多先给 5–8 条最值得改的；同类问题合并。用户要求直接改时，改完说明每处改动对应哪条原则。

## 最常用的十条（记不住其他的时至少守住这些）

1. 字号、间距、颜色、阴影都从预先定义的有限刻度里选，不临场发明数值。
2. 层次靠字重和颜色，不只靠字号；正文 400/500，强调 600/700，UI 里不用低于 400 的字重做小字。
3. 文字颜色两到三级：主要（深）、次要（灰）、三级（浅灰）。
4. 彩色背景上的次要文字用同色相、手调明度和饱和度的颜色，不用灰色，也不用白色加透明度。
5. 按钮按重要性分级：主操作实心高对比，次操作描边或低对比底色，三级操作做成链接样式；危险操作只在确认步骤里才用大红实心。
6. 能用格式和上下文说明的数据不加「标签：值」；必须加时标签弱化，数据为主（规格表等「用户按标签查找」的场景例外）。
7. 先给太多留白再收；组外间距大于组内间距，避免分组含糊。
8. 内容不必撑满屏幕：表单、卡片给合适的固定宽度或 max-width，侧边栏用固定宽度，正文每行 45–75 个字符。
9. 少用边框：优先用阴影、两种背景色或更大间距来分隔。
10. 颜色只是辅助：状态变化、图表系列同时用图标或明暗差异表达，并满足对比度（正文 4.5:1，大字 3:1）。

## 平台换算

原书以 Web/CSS 为例。其他平台按同一原则换算：

- **iOS（SwiftUI/UIKit）**：px → pt；字重 400/500/600/700 → `.regular/.medium/.semibold/.bold`；`box-shadow` → `shadow(color:radius:x:y:)` 或 `layer.shadow*`（双层阴影要用两层视图或两层 layer）；`max-width` → `.frame(maxWidth:)`；基线对齐 → `HStack(alignment: .firstTextBaseline)`。优先遵循系统的动态字体和语义色，在其之上应用层次与间距原则。
- **Android（Compose）**：px → dp/sp；阴影用 elevation 体系，原则与「阴影表示高度」一致。

数值换算后仍要落在项目刻度上；项目已有设计系统时，以项目系统为准，这里的原则用于决定「在系统里选哪个值」。
