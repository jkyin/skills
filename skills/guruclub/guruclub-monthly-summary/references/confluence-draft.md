# Confluence 草稿填写

仅在用户明确要求把本轮汇总写入指定 Confluence 页面时读取本文件。完整汇总应先在本地形成并展示可核对的表格。确认本轮纳入内容和目标后写入；已有同一内容/目标的明确授权时，无需再为增行、逐格核验和保存重复请示。内容尚未确认则保持预览，不将开始汇总的授权视为填写授权。

## 选用当前可用通道

优先发现可用的 Confluence 专用连接器/API/CLI，尤其确认是否支持用户给出的共享草稿。不要用只支持已发布页面的接口覆盖一个尚未发布的草稿。

没有适用通道时，使用已有登录会话的浏览器，并先读取所选浏览器 skill。遵循当前浏览器工具文档；不要照搬旧会话中的 tab ID、CSS 索引、浏览器客户端路径或未支持的 API。

不得提取浏览器 cookie 或令牌拼接私有接口。DOM `evaluate` 只用于读取，不调用 TinyMCE/编辑器内部 API 改写内容，不用隐藏 `fetch` 保存文档。

## 先识别与备份

1. 打开用户提供的本轮地址，确认页面标题、月份和草稿标识。历史地址属于其他月份时不能自行覆盖。
2. 读取页面 DOM 和编辑器 iframe，观察表格、标题、列名、合并单元格、现有任务行和页尾说明。
3. 将可读取的编辑前目标表格文本及结构保存到本轮 `work/`，至少包含每行单元格文本和 `colspan` / `rowspan`。
4. 找出逻辑列“目标、结果、自评”。模板可能还有“评价”列，并有姓名、部门、评分、说明和签字区域，这些不是写入目标。

不要假设一张表只有三列，也不要把一个合并单元格拆成多个逻辑列。任务行数量取决于本轮确认任务数，不能固定成 4 行或 14 行。

## 增行与写入

1. 用已观察到的正常编辑操作选中最后一个任务行，在说明和签字区域之前增加缺少的任务行。
2. 使用编辑器可见的“此后插入行”等操作，逐次验证新增行位置及列跨度。不要直接修改 DOM 来造行。
3. 从本轮正文主表提取确认的三列内容，去掉 Markdown 加粗标记，将 `<br>` 转成换行。不要把统计说明、低占比待评估表或内部证据写成任务行。
4. 通过浏览器支持的 locator 输入操作按已核实的列名映射填写“目标、结果、自评”三个逻辑单元格，不假定它们恰好是前三列。contenteditable 单元格可在工具明确支持时使用 `fill`。不要修改评价列。
5. 覆盖本轮明确要更新的旧任务内容；对于内容来源不明的现有非空任务，先保留并完成可安全填写部分，再提出具体冲突，不静默删除他人的文字。

用户明确“填充完整任务、行数不够增加行”时，页面模板建议“2～4 项”只是模板数据，不能据此删减任务。

## 写后核对

读取编辑后的 DOM，并用规范化后的全文逐一比对本地任务表：

- 确认任务行数、顺序、三列全文以及换行；不要只检查标题。
- 核对新增行的合并单元格结构、评价列、页首姓名/月份/部门/评分和页尾说明/签字区域仍被保留。
- 至少查看一次页面截图，检查实际列宽、文字显示、任务行与页尾的边界。
- 等待并观察“更改已保存”等成功状态；只输入成功而没有保存证据不能声称草稿已保存。

默认停在已保存草稿，不点击“发布”。只有用户明确要求发布时，才在完成内容和结构核对后发布。仅要求填草稿并不包含发布授权。

回报时链接目标草稿，简述填写任务数、增加行数、是否保存，以及“尚未发布”或实际发布结果。不重复整张表，不声称未完成的保存或发布。
