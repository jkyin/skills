# 报告模板与裁决

交付审查结果时读取。固定必要信息，表达与篇幅按范围调整；不强制逐项填表或展示内部评分过程。

## 结论标签

“审查结论”只写一个标签，依据在发现、范围或验证章节说明：

| 标签 | 适用条件 |
| --- | --- |
| APPROVE | 未发现达到置信度阈值的阻塞问题，相关范围已充分审查，且没有妨碍合入判断的关键证据缺口。非阻塞建议或非关键验证边界可以保留。 |
| REQUEST_CHANGES | 存在达到置信度阈值且有证据支持的阻塞问题，需要修改后复审。严重度不自动决定阻塞，须结合契约、触发条件与影响判断。 |
| INCONCLUSIVE | 尚无已确认的阻塞问题，但关键文件未审查、材料不完整或决定性证据缺失，暂时无法作出合入建议。 |

已确认阻塞问题时使用 REQUEST_CHANGES，并同时说明未完成范围，不能以 INCONCLUSIVE 掩盖已确认的问题。零发现不自动等于 APPROVE；标签本身不是平台操作。远程目标的自动报告、线程处理与平台批准按 [评论与自动处理](comments.md) 执行，并分别核验结果；REQUEST_CHANGES 不自动写入平台的请求修改状态，任何标签都不授权合入。

## 默认模板

```markdown
# 代码审查报告

## 审查结论

〈APPROVE / REQUEST_CHANGES / INCONCLUSIVE，选择一个〉

## 审查范围

目标：〈项目、审查请求或本地范围〉
比较快照：〈基准版本〉 → 〈待审版本〉
覆盖：范围内 〈N〉 项文件变更，已审查 〈R〉，未审查 〈U〉
〈未审查项及原因、明确排除范围的依据；没有则省略〉

## 已确认发现

### [I1] 〈CRITICAL / IMPORTANT / SUGGESTION〉：〈问题标题〉

位置：〈路径与行或文件位置〉
置信度：〈0–100〉

〈可达触发条件、具体后果与证据。〉
〈基准与待审版本的差异、影响范围，以及必要的契约和合入判断依据。〉

建议：〈修复方向〉

## 验证与边界

- 已检查：〈相关调用链、契约和风险〉
- 已验证：〈实际验证方法、对应版本或工具链及结果〉
- 未验证：〈影响判断的缺口及其对结论的影响〉

## 后续处理

〈所需修改、补充证据、报告/评论链接及回复、解决、平台批准的实际状态；未执行项说明原因。〉
```

## 使用规则

- 无达标发现时，发现章节只写“无达到置信度阈值的发现”，不生成空发现或凑数建议。微小改动可压缩篇幅，但保留标签、比较范围、覆盖与验证边界。
- 覆盖计数针对已确认范围内的文件变更项，N = R + U；同一路径存在不同变更状态时可以是不同项。明确排除项单列依据，不混入已审查数；范围完整性未知时说明计数仅覆盖已知材料，不能宣称全部覆盖。
- 连续复审说明上次已审版本、本次增量、复用证据的依据和发现状态变化；完整审查的覆盖计数仍针对当前完整范围，增量计数另行注明。仅查增量时明确限制，不能借用未知的前轮覆盖得出完整 APPROVE。
- 区分源码检查、最小复现、库级 CI、完整消费者构建和运行验收，并注明相关工具链；不同层级、版本或工具链的结果不能相互冒充。没有执行的验证不填写为通过，空的验证项目可省略。
- 每条发现应能独立理解，分类和阻塞依据只在需要澄清时展开。报告与发布评论使用相同发现 ID，评论无需复制整份报告。
