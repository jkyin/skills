# Guru Code Review

审查本轮改动的回归、交付契约与影响边界，以证据过滤误报，以实际影响排序。默认置信度阈值 80，可用 `--threshold N` 指定 0–100。

## 触发与范围

“审查这次变更”“review MR/PR”“检查本地改动”等请求使用本流程。已有审查评论可作为待核实的背景材料，与本轮发现直接相关的线程按已核实证据处理；不因此扩成对全部已有评论的逐条裁决。仅要求核实已有评审评论（AI 或人工）时不进入本流程。

已有评审材料包括机器人输出与人工账号发布、粘贴或转发的 AI 汇总，不能按账号身份排除。正文声明的 AI 来源、署名与审查版本分别核验；普通汇总中的相关主张同样作为背景证据，独立核对后关联处理。纯人工意见不因格式相似就被标为 AI；仅要求核实这类汇总或人工评审意见时，仍不进入独立代码审查流程。

用户同时要求独立审查与评论裁决时，分别记录范围与交付，可共享固定快照的原始材料并映射发现与原评论 ID；不互相调用，不把评论裁决代替代码覆盖与合入判断。

## 确定审查对象

- 给定审查请求（PR/MR）或两个版本时，按 [审查证据](references/evidence.md) 确定目标、比较基准与待审版本，核对完整变更、相关讨论和验证状态。未给目标时可结合当前上下文定位，只有确实有多个合理目标才询问。
- 远程材料因认证、网络或权限无法读取时，报告准确缺口；可继续已授权的本地辅助分析，不能将其冒充完整远程审查。
- 用户要求本地分支、工作区、暂存区或单个提交审查时，按 [本地范围与比较基准](references/local.md) 确定对象；不强求存在远程审查请求。
- 草稿、已合并、回退、锁文件或相同版本不自动成为跳过理由。明确要求复审就按本轮范围检查；按 [审查证据中的复审收敛规则](references/evidence.md#复审收敛) 复用仍有效的证据，检查本次增量、受影响路径与未完成项，不能把增量覆盖冒充当前完整范围的覆盖。外部写入前另核对当前目标状态。

## 建立上下文

从 diff 扩展到相关函数、调用方、状态/生命周期、依赖版本及测试，足以证明或推翻问题再下结论。修复类变更同时核对原问题的根因及相关可达入口，检查修复是否只遮住单个症状。需要时读完整文件，不强制每次全文件、全仓文档或固定数量的同类实现。

遵循当前客户端实际生效的项目指令。按改动需要读取贡献/审查规范（如项目提供的 `REVIEW.md`）及配置，关注模块的典型失败、关键不变量与有效验证方式；另一客户端的文档可提供项目事实，但其专属运行指令不自动生效。规则冲突按适用指令优先级处理，无法裁决的项目约定不作为阻塞性发现。

依靠静态证明、最小复现、实测或明确契约判断；性能问题不强制实测，但实际耗时或量化退化不能凭复杂度猜测。风格偏好、diff 未引入的旧问题、已由 linter 覆盖的格式问题不凑数。已有抑制注释是设计线索，仍核实是否掩盖本轮真实回归。

检测到 Swift/iOS 相关改动时按需读取 [Swift 证据检查](references/lang/swift.md)，其他语言不套用该清单。不要为了证明完成而运行与风险无关的测试；受影响检查通过后收尾。

## 按风险选择复核视角

微小且确定的改动可由主 agent 直接完成。涉及跨模块契约、并发、依赖变化或较多独立路径时，在环境允许且有独立价值时委派复核，选择正确性、有效项目约定、历史回归或消费者契约等视角，不固定五个 agent 或重复规范检查。

按独立风险划分复核范围。允许对关键证据进行交叉复核，避免多名检查者重复展开同一完整调查。委派与交付协议遵守当前环境的编排约束；本 skill 只规定复核内容、证据要求和结论裁决。没有独立 agent 时可以顺序检查，但如实称为单 agent 复核。

每个复核任务提供固定版本标识、必要文件、范围和验收要求，返回路径、行号、触发条件、影响和证据；可共享固定快照的原始材料，独立检查者不预先接收其他人的结论，也不以既有结论替代独立判断。主 agent 复核关键证据，去重并处理冲突。

## 发现与报告

- 置信度评价事实成立程度，严重度评价影响；高置信度不自动证明设计不合理，也不自动决定阻塞合入。多个 agent 同意不能替代证据。仅猜测的路径不达到阈值，规则类发现必须引用有效规则及来源。
- 区分本轮引入的回归、新增实现未满足明确交付契约、特定消费者的兼容性或升级风险，以及历史问题、设计限制或验证缺口。旧版本也失败而新增保证未兑现，应称为新增契约缺口，不能称为原有能力回归；历史问题不冒充本轮缺陷。
- 保留可证明的触发路径、文件/行号、基准与待审版本的差异、后果和建议修复。兼容性变化是否阻塞，要核实声明的支持范围、目标消费者与同步升级约定；本机消费者不能代表全部消费者。信息缺失作为验证边界说明，不能写成已确认缺陷；不要求机械增加分类表。
- 通过阈值后按实际影响分为严重、主要、次要三级，另行标注阻塞或非阻塞。不要把某个 API/代码模式一律定为严重，也不为填满章节发建议。
- 按 [报告模板与裁决](references/report.md) 交付，结论使用 APPROVE、REQUEST_CHANGES 或 INCONCLUSIVE；正文按范围压缩，不保留空章节。每条发现有稳定 ID，详细候选评分和过滤记录可留本轮产物。
- 交付前核对范围内文件的审查记录，未审查项须有原因；发现严重问题也不意味着其余范围已完成。无达标发现不自动得到 APPROVE，关键覆盖或证据缺口应影响裁决。结论标签与平台操作分别记录；是否实际批准按下述自动处理规则执行，始终不自动合入。

## 自动处理与完成

调用本 skill 审查明确的远程目标时，默认授权在该目标内发布确定的报告和发现、回复相关线程、解决已核实无待办的讨论；不要求先展示再逐项确认。平台 approve 默认不执行，仅在用户明确要求批准（如“满足条件就 approve”）时，于满足批准条件后执行。用户指定“只读”“先报告”“不发布”或其他范围限制时优先遵从。本地审查只交付报告，不据此推断远程写入目标。

按 [评论与自动处理](references/comments.md) 执行。事实达到阈值不自动证明动作适当：发布须有可复核证据；回复与解决须对应相关原线程；获准批准时，须为当前完整审查的 APPROVE 结论，覆盖与必要验证充分、无关键待证或阻塞事项，并核对当前版本和平台门禁。不能以部分发现确定、线程已解决或报告标签替代批准条件。

目标、证据与动作均明确时直接完成并回读，复审后结论变化也无需为同一目标重复确认；仍不明确的主张标为待证，不当作确认缺陷发布、不自动解决相关讨论或批准。只有目标歧义、需要扩面或用户限制无法裁决时询问必要信息，并继续不受影响的工作。修改代码、提交、推送和合入不包含在上述自动处理范围内。

完成后回报审查结论、已发布报告/评论、实际回复与解决状态、平台批准状态和未完成项。权限或能力不足、请求结果不明、版本变化或未完成复核均如实说明，不把拟执行或报告标签写成操作成功。

## 维护与评估

维护本 skill、调整评审提示词、模型或工具，或用户要求评估审查效果时，按 [评审效果评估](references/evaluation.md) 使用可核验样本回放，比较漏检、误报、有害建议与复审收敛情况。评估与日常审查分开，回放不沿用真实远程目标的自动写入规则；没有实际回放结果时不声称质量提升。
