# 周报表格与写作

生成表格预览时阅读本文件。最新的用户要求优先于默认模板。

## 表格列

默认与 Confluence“分支/非主线明细”对应，保持这个顺序：

| 列 | 填写规则 |
| --- | --- |
| 主线分支子任务/非主线任务 | 简短具体的一句话任务名；多项目时可加项目名 |
| 本周输出/验收口径（可测试/可验证） | 本周实际成果及可验证效果，不写 MR、CI 或审查流水账 |
| 当前阶段 | 代码已完成但未合并统一“已完成待测试”；仍在开发、方案待确认等如实填写。不要把合并等同上线或验收 |
| 状态（进行中/阻塞/已完成） | 依实际推进状态填写；有真实交付卡点才写“阻塞” |
| 阻塞/风险描述 | 真实且影响交付的风险；无已知风险可留空，不虚构风险 |
| 应对措施（含截止时间） | 有依据的措施；日期已明确时用 YYYY-MM-DD，未知不编期限 |
| 需要支持（谁/什么/截止） | 只写已知支持需求；不知道人或期限时不补写 |
| 对口人 | 留空 |
| 优先级（P0/P1/P2） | 留空 |
| 备注 | 可留空；仅必要的实质补充，不放 GitLab/仓库链接、MR 编号、分支、CI 或审查状态 |

需要应对或协作的风险，尽量在措施或支持列给出已有依据的内容；没有依据时如实说明待确认，不捏造承诺。预览保留全部待写列，“对口人”“优先级”的空值也应清晰。


## 写作口径

- 标题为简单的一句话；每项也是清楚的一句话任务名，突出“修复什么问题、增加什么功能、完成什么可验证成果”。
- 独立的功能、具体 bug 修复、有实际输出的规划各占一行；不限制为历史上的 6 行或 8 行，不为适配表格行数强行合并任务。
- 纯依赖升级汇总为一项；没有实质价值的零碎维护不单列。
- 规划、业务开发、测试和上线如实区分；工时初估不是承诺排期。
- **预览正文、备注和 Confluence 中都不放 GitLab/仓库链接、MR 编号、commit、分支名、CI/流水线状态、审查讨论、冲突和可合并性等过程信息。** 用户另行索要证据时可单独回答，不反填进周报。
- 真正影响交付的依赖、测试或产品确认问题可以用简短业务语言说明；未提供的期限、责任人、支持承诺不要杜撰。
- 默认采用清楚、简短的中文，不罗列实现细节或技术 API。多来源时用必要的项目名区分事项。
